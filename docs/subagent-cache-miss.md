# Subagent 缓存未命中：成因与三个动作

> 日期：2026-09-23
> 数据来源：本机 `~/.pi/agent/sessions`（脚本重算）+ DeepSeek 开放平台用量页
> 相关：`docs/00-subagents-token-efficiency-research.md`（讲固定成本与工具白名单，本篇讲缓存命中）、`extensions/deepseek-cache-optimizer/`（现成的前缀稳定化与命中率遥测）

## 一句话

缓存没命中不是"缓存用得不好"，是**请求发得太多、每次带的新内容太多**。subagent 每次请求的新增 token 其实比主会话更少，贵在次数。

## 机制（DeepSeek）

- 按前缀匹配：命中要求**完整匹配一个已持久化的 cache prefix unit**；共同前缀要出现 ≥2 次才会被持久化为独立单元。没有断点、没有写入控制。
- 缓存块粒度 64 token。实测命中量总是 768 / 6272 这类 64 的整数倍。
- 价格：未命中 $0.15–0.3 /M，命中 $0.003–0.006 /M（**差 50 倍**）。所以未命中虽然只占 token 的百分之几，却占输入成本的大头。
- 缓存闲置几小时到几天后清除；不像 Anthropic 那样只有 5 分钟。

## 实测数据（2026-09-22，本地日，deepseek-flash）

| 项 | 数值 |
| --- | --- |
| 总 token | 594.7M |
| 未命中 | 12.64M |
| subagent 未命中 | 7.19M（57%） |
| 主会话未命中 | 5.48M（43%） |
| subagent 派发次数 | 125 |
| 每次派发首请求 | 平均命中 3,883 / 未命中 12,128 |
| subagent 请求总数 | 5,169（每请求未命中 1,392） |
| 主会话每请求未命中 | 3,246 |

拆开看：

- **冷启动 ≈ 1.52M（12%）**：125 次派发 × 12k。每次开新 subagent 都要重读开头那一大段。
- **每轮新增 ≈ 5.7M（79%）**：5,169 次请求带入的文件内容、命令输出等。这才是主体。
- 同一波次内命中稳定在 6,272；断档或换 agent 类型后掉到 768。说明开头那段只在"连着开"时才被认出来。

## 现成的工具（别重复造）

`extensions/deepseek-cache-optimizer/` 已经在做**前缀侧**的优化：把 pi 缝在 system prompt 末尾的 cwd 动态行移出，使 system prompt 完全静态；并带 `/cache-stats` 遥测。

权威命中率数据在 `~/.pi/agent/extensions/deepseek-cache-optimizer/stats.json`（截至 2026-09-23：`cacheRead` 1,443,549,504 / `input` 18,633,602，命中率约 98.7%）。它统计的是**整个进程**，不是单个 subagent。

分工：扩展管「前缀稳不稳」，本文管「派发多不多、每次带进去多少」。两者不重叠，不要用本文的复算脚本去替扩展。

## 三个动作

1. **让 subagent 干得省。** 只读文件里要用的部分，少跑碎命令，别把大段输出回贴进上下文。针对主体那 5.7M，收益最大。
2. **合并派发。** 少开几个 subagent，每个给大一点的活。125 次降到 50 次左右，省约 0.9M。
3. **同波次保持同构。** 连着派发时用同一种 agent，中间不改 memory / `AGENTS.md` / skills（改了共同前缀单元就换，全体重新未命中）。命中能从 768 抬到 6.2k，省约 0.3–0.5M。

注意一条：**别给已经结束的 subagent 补发消息**。数据里有 3 次 `hit=0` 的全量未命中（14k–25k token），因为重新发消息会重建整个请求。

## 口径提醒

平台 9/22 显示 615.0M / 未命中 21.7M，本机全部模型加起来只有 594.9M。差额不在本机日志里 —— 同一个 API key 还有别的客户端或机器在用（推断）。

## 复算方式

数据来自 `~/.pi/agent/sessions/**/*.jsonl` 里每条 assistant 消息的 `usage` 字段：

- 未命中 = `input` + `cacheWrite`（DeepSeek 的 `cacheWrite` 恒为 0）
- 命中 = `cacheRead`
- subagent 会话的文件名形如 `..._<8-8-8-4 hex>.jsonl`（与父会话的 UUID 格式不同）；其首个 user 消息里带 `artifacts/<父会话 id>/context/` 路径
