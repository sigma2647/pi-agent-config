# 过度思考与过度探索：可用手段梳理

日期 2026-09-30。回答两个问题：模型推理太长（过度思考）怎么压，agent 反复搜无关资源（过度探索）怎么压。

前一份 `2026-09-30-deepseek-v41-overthinking.md` 记录的是 DeepSeek V4.1 这一个模型的具体处置，这份是方法层面的整理。

## 结论摘要

- 两类问题要分开治。**过度思考**是模型生成的 CoT 太长，控制点在推理请求；**过度探索**是 agent 发起的工具调用太多，控制点在 harness。把两者混在一起会选错手段。
- 证据最硬的是模型侧手段（RL 长度惩罚、logit 惩罚、budget forcing），但**外部用户用不上**，那是训练阶段的事。
- 外部用户真正能动的是三样：**effort 档位**、**提示词里的停止条件**、**harness 里的硬预算**。前两样是软的，模型可以不理；只有第三样是硬的。
- agent 侧的公开资料几乎全是工程博客，没有对照实验。可信的做法来自一个共同套路：**先定位再读、给工具调用设上限、把拦截点放在工具执行之前**。
- 本仓库已有软手段（`global/AGENTS.md` 的调查预算），**缺硬手段**。pi 的 `tool_call` 扩展钩子能拦截工具调用，是做硬预算的现成位置。

## 两类问题

| | 过度思考 | 过度探索 |
|---|---|---|
| 表现 | CoT 反复验证、自我推翻、跑飞 | 反复读同一文件、搜不相关的东西、试错式工具调用 |
| 消耗 | 推理 token、延迟 | 工具往返次数、上下文膨胀、缓存失效 |
| 谁决定 | 模型在单次请求内的生成 | agent 循环，每次工具调用是一次新决定 |
| 可用控制点 | effort 档位、提示词、max_tokens | 工具白名单、调用次数上限、钩子拦截、检索流程约定 |

过度探索还有个附带伤害：读进来的东西全进上下文，会推高后续每一次请求的成本，并增加缓存未命中。社区抱怨的「偷吃 token」多半是这条。

## 手段分层

### 第 1 层 模型侧（训练/解码期，外部用户不可控）

| 手段 | 做法 | 报告的效果 |
|---|---|---|
| 难度感知 RL | DiPO 一类，在奖励里加长推理惩罚并按难度分配预算 | 模型学会简单题少想、难题多想 |
| 标记词 logit 惩罚 | 对「but」「alternatively」这类过度思考标记词做训练无关的 logit 惩罚 | CoT 长度降 12–23%，精度持平或更好，跨 5 个模型（1.5B–32B）验证 |
| Budget forcing | 强制在预算内出答案 | 有效，但用启发式长度惩罚会连必要的推理步骤一起压掉 |
| 早停 | 检测到答案已稳定就停 | 论文结论是边际收益在高预算段明显衰减，中等预算停下能省大量算力而精度接近 |

这一层的统一结论来自《When More Thinking Hurts》：**想得越久不等于越好，更长推理与「推翻原本正确的答案」相关，最优思考长度随题目难度变化，按难度分配预算才有意义**。这解释了为什么「一律 max」会掉质量。

还有一份综述《Stop Overthinking》把现有工作分成三类：改模型本体、改推理输出（动态缩短）、改输入提示（按难度或长度控制）。我们的位置在第三类。

### 第 2 层 推理请求（软控制，用户可调）

- **effort 档位**。DeepSeek 官方 API 上 `low / high / max` 对应 50 / 75 / 100，技术报告说 60–80 能拿回大部分精度、token 不到一半。压过度思考最省事的一步。
- **关思考**。简单任务直接不发 effort、发关闭字段。
- **提示词写停止条件**。工程博客里反复出现的三句：只调用必要的工具、不重复调用相同逻辑的工具、发现关键信息就停止搜索并输出结论。
- **先给结论再解释**。把输出结构固定下来，能压缩「想完再想怎么讲」的部分。

软控制的问题很明确：**模型可以不理**。上述都是提示词，不是约束。

### 第 3 层 Harness（硬控制，真正能拦住）

| 手段 | 实现位置 | 性质 |
|---|---|---|
| 工具白名单/黑名单 | pi 的 `--tools` / `--exclude-tools` / `--no-tools` | 会话级，工具根本不可见 |
| 调用次数预算 | 扩展钩子计数，超限时返回 `{ block: true, reason }` | 硬，能中断循环 |
| 拦截并改参数 | 同一个钩子里改 `event.input` | 硬，例如强制给 `read` 加行数上限、给搜索加结果数上限 |
| 步数上限 | agent 循环的最大轮数 | 硬，兜底 |
| 上下文压缩 | pi 的 `/compact` | 事后补救，救不回已经浪费的调用 |

pi 的拦截点是 `tool_call` 事件：在工具执行前触发，可 `block`，也可以在原地改参数，后续 handler 看得到前一个 handler 的修改。这是本仓库能做硬预算的地方。

### 第 4 层 流程与架构（改变探索的形状）

- **先定位再读**。用 `grep` / `rg` 拿到 `文件:行号`，只读那一段。这条已经在 `global/AGENTS.md` 里。
- **子 agent 隔离**。把大量阅读丢给子 agent，主上下文只收结论。本仓库的 orchestrator skill 就是这个思路，属于「Isolate」。
- **缓存与去重**。同一文件、同一命令只处理一次；上下文工程里叫 Cache / Reduce。
- **确定性路由**。已知 URL 直接 fetch，不要走搜索；站内结构化内容用站点工具。本仓库的 `global/AGENTS.md` 信息获取一节已经是这个规则。

## 手段的代价

- 硬预算会**误杀合法探索**。任务未知时「读几处算够」本来就没有客观答案，卡死上限会把该读的也拦掉。
- 长度惩罚类手段会**连必要推理一起压**，论文自己指出了这个缺陷。
- 提示词级约束**可能被忽略**，尤其在长会话后期。
- effort 降档是**全量降质**，不是只砍冗余。

所以合理的顺序是：能靠流程解决的别上硬限制，能靠档位解决的别改提示词，硬限制只留给真正会跑飞的场景。

## 本仓库现状与缺口

已有的：

- `global/AGENTS.md` 的调查预算：单任务新读文件 ≤ 3、探索性工具调用 ≤ 5、同一文件只处理一次、连续两次无新信息就停、到上限给「已确认 / 未确认 / 下一步」。
- 子 agent 体系（隔离大阅读量）。
- DeepSeek 档位配置（`max` 已隐藏）。
- 会话级工具开关（`--tools` 等）可用但没在用。

缺的：

- **没有任何东西会真的阻止越界**。调查预算是提示词，模型可以超。
- 没有调用计数或步数上限的兜底。
- 长会话场景（大上下文 + 连续工具调用）没有专门处理，而社区报的死循环恰好集中在这里。

## 如果要做，按这个顺序

1. **先验证现象还在不在**。本仓库 2026-09-30 的 7 次实测没有复现过度思考（见前一份文档），所以第一步是零成本：不动配置，先观察几个真实长任务。
2. **低成本**：对日常任务用 `low`，只有明确的难题用 `high`。`max` 已隐藏，不用管。
3. **中成本**：把「先定位再读」和「停止条件」写进任务模板，让每次任务都带上，而不是指望模型记得全局规则。
4. **高成本（唯一真正硬的）**：写一个 pi 扩展，订阅 `tool_call`，按会话计数，超过阈值后拦截并回一条说明，或者只对「重复调用同一参数」的情况拦截。这条能兜住死循环，代价是可能误杀。

第 4 条要不要做，取决于第 1 步的观察结果。现在就上属于对没验证的问题做过度设计。

## 未确认

- agent 侧的公开资料（上下文工程、钩子拦截）基本都是工程博客和实践总结，没有对照实验。上面的「共同套路」是归纳，不是被验证的结论。
- 模型侧论文的指标是推理 benchmark 上的 CoT 长度和准确率，**不是 agent 场景的工具调用次数**，两者不能直接换算。
- 本仓库 7 次实测样本小、任务短，只能说明「小任务上没有复现」，不能说明长任务也没问题。
