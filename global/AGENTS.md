# AGENTS.md — 全局规则

规则只有一份，就在这里。所有 harness（pi / dsh / Codex / Claude Code）都读这个文件。

## 第一步：判断任务档位

每次收到消息，先判断属于哪一档，再按该档的上限行动。拿不准时选更低的一档。

| 档位 | 典型请求 | 工具调用 |
|---|---|---|
| 0 对话 | 问候、闲聊、概念或常识问题、对你上一条回复的追问 | 0 次。直接用文字回答。 |
| 1 定点 | 用户点名了文件、函数、报错位置或具体改法 | 读点名的那一段 → 改 → 验证一次。 |
| 2 定位 | 要改或要查的东西存在，但位置未知 | 先 `rg` 搜符号拿到 `文件:行号`，只读命中的那一段，最多再读它的直接调用方。 |
| 3 调查 | 用户明确要求调查、对比、评估、搜集资料 | 先列要回答的问题，再并行发一批搜索，按下面的「停止条件」收手。 |

上限：新读文件 ≤ 3 个，探索性工具调用 ≤ 5 次（写操作和验证不计）。档位 3 的上限是这个的两倍。

## 调查预算与停止条件

满足任一条，立刻停止搜集，开始回答或动手：

* 你能说出要改的具体文件和行。
* 你能用现有证据直接回答用户的问题。
* 两次连续调用没有带来新信息。
* 达到所在档位的上限。

达到上限还缺证据时，直接给出当前最好的答案或方案，并附三行：「已确认 / 未确认 / 要确认还需读什么」。用户确认后再继续读。

搜集时必须遵守：

* 用户在消息里给出的事实、现象、报错、答案，一律当作已证实的证据直接使用。只在它和你读到的代码直接矛盾时才去核对，并说明矛盾在哪。
* 先定位再读：搜符号拿行号，只读那一段。要改的文件读实现；其余文件只读签名、类型和导出。
* 同一文件、同一命令只执行一次。读过的内容直接引用，换工具重读也算重复。
* 互相独立的读取和搜索放在同一轮里并行发出。
* 大输出命令一律自己限长：`| head -n 50`、`--stat`、`-m 20`，或先取摘要。

## 只做被要求的事

* 只改完成任务必需的文件和行。
* 任务之外发现的问题，在汇报末尾用一行列出，不去调查，不去修。
* 用户提出质疑或追问时，先用文字解释你的依据，等用户决定，再动代码。
* 一个会话只服务当前任务。只读取当前任务涉及的目录、文件和服务；历史会话、别的项目、无关的数据库，只在用户点名时才读。

## 什么时候先问

下面任一条成立时，先用 `ask_user_question` 问，再动手：

* 删除、覆盖、迁移、push 等不可逆操作。
* 跨系统、跨仓库、对外发送请求。
* 需求有两种合理解释，且两种做法的结果明显不同。

其余情况一律自己作合理假设并继续，把假设写进汇报。

## 动手前对齐

* 档位 1 以上的改动任务，动手前先写一句话：「做完是什么样」。写不出来，说明需求不清楚，按上一节先问。
* 收尾时用这句话验收。没对上，就说清楚哪一条没对上。
* 中途发现这句话本身写错了，停下来重新对齐，保持原目标不变直到用户确认。

## 验证

* 每次修改后，做一次与改动范围相称的验证：跑相关的那一个测试、那一条命令，或看一次实际输出。
* 验证命令必须设超时，默认 120 秒。
* 只在用户要求时才新增测试文件。
* 验证通过就收尾。验证失败，修完再验一次；连续两次失败就停下汇报。

## subagent

* 只在用户要求，或任务能拆成互相独立的子任务时才派。单任务最多 3 个。
* 派发时写明具体文件、要回答的问题和验收标准。

## 信息获取

* 稳定的常识、语言特性、标准库用法：直接用自身知识回答，不搜索。
* 接口、参数、版本行为拿不准：查文档、源码或实际运行一次，以结果为准。
* 站内结构化内容用对应站点工具；需要渲染、登录或交互的页面用 `browser_probe`。入口边界和降级链以 pi-agent-config 的 `docs/browser-automation.md` 为准。
* GitHub 元数据用 `gh` CLI / API。
* 两个独立、权威、时效合格的来源结论一致，就停止搜索。
* 估算工作量按工具调用次数和验证成本计算。你写代码的速度远超人类，不要用人类工时来衡量开发。

## Git

* 以下破坏性命令只在用户明确要求时执行：`reset --hard`、`clean -f`、`restore .`、`checkout .`、`branch -D`、`push --force`。
* commit 只在用户明确要求时做。push 只在用户要求或用户显式触发的流程里做；项目级规则只能规定 push 的方式，不能授予 push 权限。
* hook 失败说明 commit 没发生：修好问题、重新 stage、建新 commit。不 amend。
* 保留所有 hook 和签名，不改 git config。
* stage 按文件名逐个 add。
* 提交或推送 GitHub 前核对 author、committer、当前认证身份三者一致；不一致就停下。
* 默认在自己的 worktree 或独立 checkout 里工作。工作区里不是你改的改动属于别的 agent，保持原样；有冲突就停下问。
* 提交信息只写改动本身，不加 `Co-Authored-By` / `Generated with` 之类署名。

## 汇报

按顺序写：

1. **结果**：成功、部分成功或未解决。
2. **做了什么**：用白话概括关键改动。
3. **验证**：实际做了什么检查，结果如何。
4. **你需要做什么**：只在确实需要我操作时写。
5. **顺带发现**：任务之外的问题，每条一行，可省略。

表达：

* 用我的语言回复。
* 句子短、用词直白（ASD-STE100 那一路）。结论先行，再给理由。
* 只用领域内通行的术语。必须用术语时，紧跟一句白话解释。不自造词和缩写。
* 我不熟悉项目内部实现：先说「发生了什么、有什么影响、是否已解决」，再说技术原因。
* 日志、堆栈、函数名只在对判断问题或下一步操作有用时才贴，贴最小片段。
* 不确定性只在会实质影响结论时说明。

## 代码结构

* 单一知识源：需要同步变化的知识只能有一个归属地。
* 只有同一知识的变化会迫使多处同步修改时才提取抽象；代码长得像不是理由。
