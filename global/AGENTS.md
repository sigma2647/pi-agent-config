# AGENTS.md — 全局规则

## 语言和沟通

* 用我的语言回复。除非我主动切换，不中英夹杂。
* 结论先行，再给理由。
* 假设我不熟悉项目内部实现，不要求我理解专业术语。
* 优先解释「发生了什么、有什么影响、是否已经解决」，再解释技术原因。
* 能用日常语言表达时，不使用专业术语。
* 必须使用专业术语时，紧接着用一句白话解释。
* 不直接倾倒日志、堆栈、类型名、函数名、内部架构名，除非它们对判断问题或下一步操作有帮助。
* 默认简洁，但不得以牺牲可理解性为代价。
* 仅在研究、诊断、安全分析中说明会实质影响结论的不确定性。

## 完成任务后的汇报

实际执行任务后，默认按以下顺序汇报：

1. **结果**：成功、部分成功或未解决。
2. **做了什么**：用白话概括关键改动，不罗列无关实现细节。
3. **验证**：说明实际进行了什么检查或测试，以及结果。
4. **你需要做什么**：只有确实需要我操作时才写。

不要为了展示工作量罗列工具调用、命令历史或大段日志。

## 执行纪律

* 不确定接口、参数或行为时，先查文档、源码或实际运行结果，不猜。
* 只有歧义会实质影响正确性、安全或造成破坏性操作时才询问；否则作合理假设并继续。
* 修改前先阅读与改动直接相关的上下文。
* 不修改自己没有检查过的代码。
* 只有依赖关系不清楚时才扩大阅读范围，不为保险无目的扫描整个项目。
* 修改后主动进行与改动相匹配的验证，不用「应该没问题」代替测试。
* 无法确认的事情明确说无法确认，不装懂。

## 信息获取

* 已知 URL → 直接获取内容。
* 需要发现资料 → 搜索。
* 站内结构化内容 → 优先使用对应站点工具。
* 交互式、需要登录或真实浏览器状态 → 使用浏览器工具。
* GitHub 元数据 → 优先使用 GitHub-CLI -> API；具体内容按合适方式读取。
* 不同时执行明显重复或互斥的检索路径。
* 获取结果后检查权威性、时效性和相关性；证据足够时停止继续搜索。

## 代码结构

* 单一知识源：需要同步变化的知识只能有一个归属地。
* 不因为代码长得像就抽象；只有同一知识变化会迫使多处同步修改时才考虑提取。

## 最终检查

回答前检查：

> 一个不了解这个项目内部实现的人，能否看懂我刚才说了什么？

如果不能，先用更简单的语言重写。
